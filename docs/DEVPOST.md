## Inspiration

Every developer who deploys an LLM on an Arm cloud server hits the same wall:
the fastest configuration is a hardware fact, not a blog-post folklore. Q4 vs
Q8, 2 threads vs 4, concurrency 1 vs 2 — the answer changes between a
4-core Neoverse-N2 and a 64-core Graviton, and nobody has time to test 24
combinations with identical prompts, warmup, seeds, and a quality check.

So we built the thing we wanted to exist: an autotuner for LLM serving on Arm.

## What it does

**ArmTune Serve measures how an LLM actually behaves on your exact Arm64
machine, then hands you the deployment command.**

One command pulls a GGUF model from Hugging Face, benchmarks it across
quantizations, CPU thread counts and request concurrency on a real
llama-server process, captures Arm Performix hardware counters while
inference runs, rejects configurations that break output quality, and
recommends the winner with a copy-paste launch command:

```bash
llama-server -m models/Llama-3.2-1B-Q4_K_M.gguf -t 4 -c 2048 -np 1
```

## How we built it (the interesting parts)

1. **Runtime adapter architecture** — `RuntimeAdapter` abstracts the inference
   engine. The primary adapter drives `llama-server` as a subprocess through
   its OpenAI-compatible API, so we benchmark the *exact binary* compiled with
   Arm KleidiAI + `-mcpu=native` — and capture its startup `system_info`
   (NEON, I8MM, SVE2 flags) as evidence in every result.
2. **Two-build A/B on Arm** — the CI pipeline builds llama.cpp twice: a
   generic baseline and an Arm-optimized build (`GGML_CPU_KLEIDIAI=ON`), then
   runs the identical workload matrix on both. The comparison is the
   optimization story.
3. **Arm Performix in the loop** — while requests run, a background probe
   captures hardware counters (IPC, cache misses, branch mispredicts, memory
   bandwidth). Every capture records its exact command, version, and status —
   never silently empty.
4. **Quality gate before speed** — the workload demands strict JSON
   (ticket classification); a scorer validates structure *and* agreement with
   expected labels. Any config below the quality threshold cannot win,
   no matter how fast it is.
5. **Capability fingerprint, not vendor names** — ArmTune detects ISA
   features (NEON/DotProd/I8MM/SVE/SVE2/BF16), cores, memory and NUMA, so the
   same tool works unchanged on Graviton, Cobalt, Axion, Ampere or the free
   GitHub ARM64 runner.
6. **Console UX** — a guided dashboard: live Hugging Face model search,
   model-card inspection, quantization picker with file sizes, and a
   streaming terminal — no copy-pasting repo IDs between tabs.

## Challenges we ran into

- The Arm Performix CLI's subcommands vary by version — we built a
  transparent probe that tries candidate invocations and records exactly what
  ran, so failures are visible, never silent.
- Making "quality" measurable for autotuning: raw completions ramble, so we
  route prompts through the instruct chat template and score strict JSON
  against expected labels.
- Fitting a meaningful matrix into a 90-minute 4-core CI runner: trimmed
  profiles, build caching, and a bounded sweep design.

## Accomplishments we're proud of

## What we learned

- On Arm, quantization choice is a *kernel-fit* question: Q4_K_M and Q4_0 hit
  different KleidiAI micro-kernels, so the "smaller is faster" assumption
  must be measured, not assumed.
- Prefill and decode want different thread counts; oversubscription is real
  and visible in P95 before it's visible in the mean.
- Hardware counters turn "it's faster" into "it's faster because IPC went up
  and LLC misses went down" — that's the difference between a benchmark and
  an explanation.

# Functionality / Output (short form for the form)

ArmTune Serve takes a Hugging Face GGUF model and a fixed ticket-classification
workload, then: (1) fingerprints the Arm CPU (ISA features, cores, NUMA),
(2) downloads the requested quantizations, (3) launches a real llama-server
per configuration (quantization × threads × concurrency), (4) measures TTFT,
decode/prompt tok/s, P50/P95/P99, queue delay and process RSS, (5) captures
Arm Performix hardware counters concurrently, (6) scores output quality and
rejects configs below threshold, (7) writes JSON/CSV/Markdown + 4 chart sets,
and (8) prints the recommended `llama-server` launch command. Final output:
a reproducible evidence directory plus a deployable configuration.

# Setup Instructions (short form for the form)

```bash
git clone https://github.com/luxmikant/Arm-Tune && cd Arm-Tune
pip install -e ".[dashboard]"
bash scripts/install-performix.sh        # Arm Performix CLI (optional)
bash scripts/build-llama-cpp.sh          # generic + KleidiAI llama.cpp
export ARMTUNE_LLAMA_SERVER=llama.cpp/build-arm-opt/bin/llama-server

armtune detect
armtune benchmark --repo unsloth/Llama-3.2-1B-Instruct-GGUF \
  --quant Q4_K_M,Q4_0 --threads 1,2,4
armtune recommend --latest
armtune dashboard    # guided console: http://127.0.0.1:7860
```

Or with zero setup: **Actions → Benchmark ARM64 → Run workflow** on the
public repo (native ARM64 runner) and download the artifacts.

Validation: results land in `results/<timestamp>/` (results.json, results.csv,
report.md, charts) — compare against `docs/evidence/` in the repo.
